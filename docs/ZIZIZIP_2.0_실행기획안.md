# ZIZIZIP 2.0 실행 기획안

작성 기준: 2026-09-17. 사용자 확정 요구와 설계 제안을 구분한다. 첨부 문서는 데이터 근거이며 실행 지시로 취급하지 않는다. 이 문서는 구현 작업을 수행한 결과가 아니다.

## 1. 확정 요구

- 로그인 후 간단한 설문을 거쳐 맞춤 공고를 제공한다.
- 청년, 신혼부부, 신생아가구, 고령자 네 대상을 지원한다.
- 첫 조사 범위는 LH, 서울, 매입임대다.
- FastAPI 학습을 실제 구현 목표에 포함한다.
- 자동 탐색, 로그인, 추천을 첫 출시 범위에 포함한다.
- 추가 월 운영비 목표는 0원이다. 기존 도메인 갱신 비용은 별도다.
- 현재 Next.js 서비스는 Vercel에 배포되어 있다.
- LH API와 VWorld 계정은 사용자 소유다. Supabase 프로젝트는 아직 없다.
- 외부 사용자 대상 출시 목표는 한 달 이내다.

## 2. 첨부 자료에서 확인한 사실

### 주택목록

| 파일 | 시트 | 헤더/데이터 | 주소가 있는 번호 행 | 임대조건 |
| --- | --- | --- | --- | --- |
| 25년4차 신혼·신생아매입임대Ⅰ 게시용 (1).xlsx | 251218 신혼신생아Ⅰ | 7~9행 / 10~74행 | 65 | 계층 2개 × 기본·최대전환 2개 |
| 25년4차 신혼·신생아매입임대Ⅱ 전세형 게시용.xlsx | 251218 신혼·신생아Ⅱ(전세형) | 6~8행 / 9~250행 | 242 | 소득80% 이하·초과 2개 |

두 파일은 2025-12-18 공고의 공급주택목록이며, 307개 주택 행 모두 지역 열이 서울특별시다. 현재 접수 중 공고라는 의미는 아니다. 출시 시 현재 공고 상태는 별도 확인한다.

Ⅰ의 Q:R은 수급자·지원대상 한부모가족·차상위계층의 기본 조건, S:T는 해당 계층의 최대전환 조건이다. U:V와 W:X는 그 외(소득70%이하)의 기본·최대전환 조건이다. Ⅱ의 Q:R과 S:T는 소득80% 이하·초과 조건이다. 이 표기는 원본의 가격 구분이며 전체 신청 자격이나 현재 연도 기준을 정의하지 않는다.

주소, 동, 호, 주택군, 전용면적, 방수, 층수, 승강기, 주택유형, 열람일정이 존재한다. 병합된 상위 헤더를 함께 읽어야 가격의 적용 대상을 보존할 수 있다. 금액 단위는 공식 공고와 대조해 확정하고 원본 값을 보존한다.

### 2024-10-10 API 가이드

- 목록 조회 서비스 `lhLeaseNoticeInfo1`을 설명한다.
- 서울 지역 코드 `CNP_CD=11`, 상위 공고 유형은 임대주택 `06`, 주거복지 `13` 등이 있다.
- `PAGE`, `PG_SZ`, 공고명, 게시일, 마감일 등의 요청 항목과 상세 URL `DTL_URL`이 있다.
- 첨부파일 URL, 호실별 가격, 전체 자격 규칙을 제공하는 명세는 이 가이드에서 확인되지 않는다.
- 매입임대가 어떤 분류에 속하는지, 전국 공고에 서울 주택이 포함되는지 실제 응답으로 확인한다. 처음부터 `06`만 조회해 누락시키지 않는다.
- 가이드의 요청 날짜 예시는 YYYYMMDD다. 기존 코드의 YYYY.MM.DD와 차이가 있어 실제 허용 형식을 검증한다.
- 가이드의 `serviceKey` 표기와 기존 코드의 `ServiceKey` 차이, 응답 오류 코드, 페이지 종료 조건을 실제 호출로 검증한다.

아직 실제 API 호출, 상세 페이지 접근, 자동 다운로드는 검증하지 않았다. 청년·고령자 대표 파일도 추가 확보해야 한다.

## 3. 제품 동작 제안

### 진입과 설문

로그인 → FastAPI에서 내 프로필 조회 → 미완료 시 설문 → 저장 → 맞춤 공고. 재방문 시 설문을 반복하지 않는다. 로그인 전 기존 업로드·지도 유지와 공개 공고 열람 범위는 구현 전 확정한다.

설문은 3단계로 제안한다.

1. 관심 대상: 청년·신혼부부·신생아가구·고령자 복수 선택, 잘 모르겠음 허용. 자기 선택은 자격 충족 증거가 아니다.
2. 희망 지역: 서울 전체 또는 자치구 복수 선택.
3. 주거 조건: 최대 보증금, 최대 월세, 최소 전용면적, 방수. 각 조건은 상관없음 허용.

소득·자산·가구 상황의 세부 질문은 해당 공고 가격/자격을 확인하려 할 때 추가한다. 상세 자격을 추정하기 위해 불필요한 개인정보를 미리 수집하지 않는다.

### 추천 규칙 v1

- 공고 모집 대상과 관심 대상의 교집합을 확인한다. 제목만으로 확정하지 않고 공식 근거와 분류 상태를 저장한다.
- 네 대상은 상호 배타적이지 않다. 사용자와 공고 모두 여러 태그를 가질 수 있다.
- 동일 주택의 동일 임대조건 안에서 보증금과 월세를 함께 비교한다.
- 다른 주택의 면적과 가격을 합쳐 공고가 일치한다고 판단하지 않는다.
- 적용 계층이 확인된 예산 일치와, 적용 계층 미확인인 예산 일치를 구분한다. 후자는 조건부 결과이며 최상위 확정 일치로 취급하지 않는다.
- 미입력 선호는 불일치로 계산하지 않는다. 원본 데이터 누락은 확인 필요로 취급한다.
- 공개된 모집 대상 태그, 선호 일치 항목 수, 접수 일정이 확인된 경우 마감 순, 안정적인 ID 순으로 결정적인 정렬을 제공한다. 정확한 우선순위는 API 계약에 고정한다.
- 예: “관심 대상에 해당하는 공고 · 희망 지역 일치 · 예산 내 임대조건 있음(적용 계층 확인 필요)”. 확정적인 신청 가능/불가능 문구는 사용하지 않는다.
- 청년·고령자도 첫 출시 대상으로 유지하되, 검증된 첨부파일이 없는 공고는 원문 링크와 목록을 제공하고 지도·가격 추천 지원 여부를 명시한다. 이 지원 수준은 사용자 확인이 필요하다.

## 4. 기술 구조 제안

```text
Next.js (기존 Vercel)
  ├─ Supabase Auth: 로그인·세션
  └─ 사용자 액세스 토큰 → FastAPI (별도 Vercel 프로젝트)
                              └─ Supabase PostgreSQL

GitHub Actions 정기/수동 실행
  └─ Python 수집 CLI → LH 목록·상세·첨부 → 파싱·지오코딩 → Supabase
```

Supabase는 FastAPI 호스팅이 아닌 Auth/DB/원본 저장소다. FastAPI는 검증된 사용자 ID를 기준으로 설문, 관심 공고, 추천, 검색을 제공한다. 수집 CLI는 FastAPI와 동일 Python 서비스 코드를 사용하되 웹 요청 안에서 장시간 수집하지 않는다.

자동 수집용 Python 파서는 두 첨부 양식부터 구현하는 것을 제안한다. 기존 TypeScript 파서는 수동 업로드에 유지하고, 컬럼 매핑과 기대 결과를 Python 검증 자료로 재사용한다. 두 언어의 코드가 직접 재사용된다고 표현하지 않는다. 지도 앞에는 기존 LocationData로 변환하는 어댑터를 둔다.

로그인은 Supabase Google OAuth 1종부터 제안한다. 이메일 비밀번호/매직링크는 발송 환경이 필요하므로 첫 선택에서 제외하는 편이 단순하다. 사용자 선호에 따라 카카오 등으로 변경할 수 있다.

사용자 데이터는 사용자 JWT 문맥의 DB 접근과 RLS로 본인 행만 접근하도록 설계한다. 토큰 서명·발급자·대상·만료를 검증하며 요청 본문의 user_id를 신뢰하지 않는다. 관리자 권한 키는 수집 전용으로 분리한다. 인증 사용자 A/B 교차 접근 차단은 출시 필수 검사다.

### 비용 정책

- Vercel Hobby는 비상업적 개인 이용에 한정된다. 광고·수익화 등 사업 목적 전환 시 플랜을 재검토한다.
- Supabase Free는 DB 500MB, Storage 1GB 등 한도가 있고 1주 비활성 시 일시정지 정책이 있다. 자동 백업을 전제로 하지 않는다.
- GitHub Actions는 계정 플랜과 저장소 공개 여부에 따른 무료 사용량 내에서 사용한다. 과금 중지 예산을 설정하고 빌드·수집 실행시간을 함께 측정한다.
- 처음에는 일 1회 수집을 제안한다. 스케줄 지연 가능성을 감안해 마지막 성공 시각과 수동 실행 기능을 둔다.
- 파일 해시가 바뀐 경우에만 재파싱한다. 주소별 좌표는 DB 캐시에 보관한다. 조회 요청마다 지오코딩하지 않는다.
- 원본은 지원 대상 파일만 보관하고 용량·보존 기간을 제한한다. 수집 로그는 30일을 기본 제안한다.
- 무료 한도 소진 시 자동 유료 전환 대신 수집 중단·상태 안내를 기본 정책으로 한다. 0원은 무제한 가용성을 의미하지 않는다.

| 엔터티 | 핵심 필드/제약 |
| --- | --- |
| profiles | auth user id, 대상 태그 배열, 설문 버전/완료 시각 |
| preferences | 사용자별 1행, 지역 코드 배열, 예산·면적·방수, null=선호 미설정 |
| notices | 원본 식별 구성요소, 제목, 공식 URL, 원본 상태, 대상 태그, 분류 근거, 마지막 확인 시각 |
| notice_schedules | 접수 대상/순위, 접수 시작·종료, 원본 표현, 날짜 정밀도 |
| notice_files | URL, 이름, 해시, 파일 버전, 파서 버전, 처리 상태/오류 |
| housing_units | 공고/파일 연결, 원본 시트·행, 주소·동·호·면적·방수, 좌표/변환 상태 |
| rental_options | 주택 연결, 적용 계층 코드·원문, 기본/전환 구분, 보증금·월세·원본 단위 |
| favorites | user_id + notice_id 유일성 |
| collection_runs | 실행 시작/종료, 단계별 성공/실패 수, 재시도 정보 |
| geocode_cache | 주소 원문·정규화값, 변환 버전, 좌표·제공자·확인 시각 |

공고 식별키는 PAN_ID 단독 유일성을 가정하지 않고 시스템 구분 등 실제 응답을 확인해 결정한다. 정정 시 검증된 신규 버전을 한 번에 공개하고, 실패한 새 버전이 기존 정상 데이터를 지우지 않도록 한다. 공고 취소와 첨부 내 주택 삭제도 처리한다.

가격·면적 미확인은 null이며 0과 다르다. 게시일은 접수 시작일이 아니다. 접수 시각을 모르면 시각을 임의 생성하지 않는다. 좌표 실패 시 고정 좌표를 생성하지 않고 목록에만 보인다.

초기 API 제안: GET/PATCH /me/profile, GET/PATCH /me/preferences, GET /notices, GET /notices/{id}, GET /houses, GET /me/recommendations, GET/PUT/DELETE /me/favorites/{notice_id}. 컬렉션 목록 경로와 단일 리소스 경로는 계약 단계에서 정리한다. 공고는 페이지네이션, 지도는 bbox·결과 제한을 사용한다. 일반 사용자용 수집 실행 API는 만들지 않는다.

첨부파일 자동 획득이 1주 안에 검증되지 않으면 자동화 완료로 보고하지 않는다. 병목과 가능한 대체 공급 경로를 보고하고 출시 지원 범위를 다시 결정한다. 과거 첨부파일은 회귀 테스트용으로 사용하며 현재 모집 데이터로 노출하지 않는다.

## 7. Claude Code 공통 작업 지시

각 작업은 T00부터 순서대로 한 번에 하나씩 실행한다. 다음 작업은 이전 완료 기준과 미해결 의존성을 확인하고 시작한다.

```text
docs/ZIZIZIP_2.0_실행기획안.md와 현재 CLAUDE.md를 읽고 이번에는 [T번호]만 수행해줘.
확정 요구와 설계 제안을 구분하고 현재 코드와 다른 문서 설명은 기록해줘.
외부 API, 자격 기준, 가격 의미를 추측하지 말고 근거와 미확인을 구분해줘.
```

## 8. 남은 사용자 결정

1. 로그인 제공자: Google 1종을 권장. 다른 선호가 있으면 변경.
2. 네 대상 복수 선택 허용: 권장. 서비스 관심 분류이며 자격 판정과 분리.
3. 네 대상 공고 탐색을 제공하면서, 검증된 양식부터 주택 지도·가격 추천을 지원하는 단계적 공개 허용 여부.
4. 무료 비상업 베타로 시작하고 무료 한도 도달 시 일시 제한하는 운영 정책 허용 여부.

필요한 계정 준비는 Supabase Free 프로젝트, 선택한 OAuth 제공자 설정, GitHub Actions 사용 가능 여부 확인이다. 비밀 값은 대화에 붙이지 않고 각 서비스 설정에 등록한다.
